### 5. Three follow-up mechanisms + three more tests

Three previously-flagged gaps were closed in commit `113ca34`:

- **New parser token `trigger_bcast N`** in
  `connection_matrix.cpp`. Sets `c->is_bcast=true`,
  `c->trigger=N`, `c->start=TRIGGER_START` in one step, so a
  broadcast can be started by a named trigger instead of a fixed
  time. The existing "both start time and trigger" parser guard
  still passes because `c->start == TRIGGER_START`. Enables
  trigger-started broadcasts and chained broadcasts.

- **Sink-side completion firing for `recv_done_trigger`** in
  `uec.{h,cpp}`. Previously `UecSink::_end_trigger` was stored
  but never activated, so `recv_done_trigger` on a regular P2P
  flow was silently a no-op. Added an opt-in
  `set_expected_bytes(n)` setter (default 0 preserves backward
  compatibility) and a byte-count check in
  `UecSink::receivePacket` that fires `_end_trigger` once
  `_cumulative_ack` covers `_expected_bytes`. Wired in
  `main_uec.cpp`'s P2P branch whenever `recv_done_trigger` is
  specified.

- **New tests T07--T09** exercising the three changes:
  - T07 trigger_started_bcast --- P2P `send_done_trigger` fires
    the named trigger which launches all 6 bcast legs together
  - T08 bcast_chain --- bcast1 `recv_done_trigger` → named
    trigger → bcast2 via `trigger_bcast`; two cascaded broadcasts
  - T09 p2p_recv_done_trigger --- regression test for the
    previously latent `UecSink` no-op: before today's fix the
    named trigger would never fire; T09 asserts it now does

All 9 tests pass against the current binary.
