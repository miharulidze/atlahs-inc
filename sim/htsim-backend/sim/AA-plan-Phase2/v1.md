# Phase-Two Plan — Switch-Level Multicast Replication for Broadcast

*Proposal. Reviewed codebase via four parallel Explore agents before
writing. No code changes have been made; please approve, amend, or
reject before implementation begins.*

---

## 1. Recap: What Phase One Delivers, What Phase Two Must Add

Phase one (merged) emulates `MPI_Bcast` by decomposing one broadcast
into \|G\|-1 unicast legs. The root runs \|G\|-1 `UecBcastSrc`
instances and pushes |G|-1 packets out of its 100 Gbps uplink, one
after another. That serialisation is the bottleneck and produces
the linear completion-time curve reported in Chapter~4.3 of the
thesis (≈339 ns per added leg).

**Phase two introduces the network-side multicast mechanism.** The
root emits *one* packet; the fabric replicates it so that \|G\|-1
copies are delivered without the root-uplink bottleneck. The
completion-time curve should become approximately *constant* in
\|G\|, dominated by the farthest leaf's path latency and the
worst-case branching factor, not by linear-in-\|G\| serialisation.

The phase-one benchmark harness and the sink/barrier completion
orchestration are carried over **unchanged**. Only the sending
endpoint and the fabric-internal routing change.

## 2. Ground Truth from the Codebase (agent findings)

### 2.1 Switch forwarding is two-stage and strictly unicast

`FatTreeSwitch::receivePacket` (`fat_tree_switch.cpp:23`) runs a
two-step pipeline per packet:

1. **Ingress**: look up FIB via `getNextHop(pkt)`
   (`fat_tree_switch.cpp:321`), attach the chosen `Route` to the
   packet, then delay via `_pipe->receivePacket(pkt)`.
2. **Egress**: remove from `_packets` tracking and `pkt.sendOn()`
   along the attached route.

The FIB is strictly destination-keyed:
`RouteTable::_fib : unordered_map<int, vector<FibEntry*>*>`
(`routetable.h:52`). The `vector<FibEntry*>` is the ECMP
alternatives list; `getNextHop` picks exactly one of them via a
hash of `flow_id` and `pathid`. Packets carry single-path state
(`_dst`, `_pathid`, `_route`, `_nexthop`) and take exactly one
route per hop. **No code path anywhere in htsim fans a single
packet out to multiple egress ports today.**

### 2.2 `FatTreeTopology::set_up_mcast` is a no-op stub, correctly placed

Defined at `fat_tree_topology.cpp:596`, printing
`"set_up_mcast unimplemented"` when `groups != nullptr`. It is
invoked from `main_uec.cpp:781`, after the topology is built and
`conns->groups` is attached, but *before* any per-flow `UecSrc` /
`UecSink` is instantiated. This is the correct time to install
static multicast FIB state on switches.

The topology exposes:

- `switches_lp / switches_up / switches_c` for TOR / AGG / CORE
  switches respectively;
- `queues_ns_nlp`, `queues_nlp_nup`, `queues_nup_nc`, and their
  reverses — `[from_tier_id][to_tier_id][bundle]` indexed;
- `HOST_POD_SWITCH(host)`, `MIN_POD_AGG_SWITCH(pod)`,
  `MAX_POD_AGG_SWITCH(pod)`;
- `FatTreeSwitch::switch_type` (`TOR` / `AGG` / `CORE`) via
  `getType()`.

Everything needed to compute a replication tree deterministically
is available.

### 2.3 Packets have a ref-count that could support non-clone fanout…

`PacketDB` uses `inc_ref_count` / `dec_ref_count`
(`network.h:274–312`): a packet is only freed when the refcount
reaches zero. In principle one packet object could be delivered to
multiple egress ports with `inc_ref_count(N)` and each
queue/sink decrementing on consumption.

### 2.4 …but fanout *must* use distinct packet objects, not one shared

A single packet carries path state (`_route`, `_pathid`,
`_nexthop`, `_direction`). Different replicas take different
paths and must have different values for those fields. Sharing one
packet object across replicas therefore does not work.

`UecPacket::newpkt(UecPacket &source)` (`uecpacket.h:45`) already
exists: it allocates a fresh packet from the PacketDB pool and
copies metadata. This is the canonical way to spawn a replica.

### 2.5 No pre-existing multicast anywhere

Searched `uec.cpp`, `eqds.cpp`, `ndp.cpp`, `tcp.cpp`, `roce.cpp`,
`swift.cpp`, `hpcc.cpp`, `strack.cpp`, `switch.cpp`,
`compositequeue.cpp`, `queue.cpp`, `tests/`. No replication,
fanout, or multicast route support outside the stub. Tests do not
exercise one-to-many delivery. Phase two is a from-scratch
extension.

### 2.6 Consequence for the design

The cleanest structural insertion point is
`FatTreeSwitch::getNextHop` + `FatTreeSwitch::receivePacket`:
teach them that a specific class of destinations means "fan me
out along the pre-installed tree instead of picking one ECMP
alternative". The replication unit is one fresh `UecPacket` per
egress, produced via the existing `UecPacket::newpkt(source)`
copy factory.

## 3. Design Decisions

Each decision lists the alternatives, the trade-offs, and a
recommendation. All recommendations are subject to approval.

### 3.1 Where does replication happen?

**Three candidates.**

- **(α) Ingress-only at the root's TOR.** The root's TOR sees one
  incoming packet and emits \|G\|-1 copies toward the destination
  TORs directly.
- **(β) Tree replication.** Every switch on the multicast tree
  receives one packet and emits one copy per downstream branch
  (typically 2–K copies). Matches real hardware (NVIDIA SHARP,
  Broadcom Scorpion).
- **(γ) Hybrid.** Ingress fans out by pod; per-pod AGGs fan out by
  TOR.

(α) is the simplest but **reintroduces the same root-uplink
bottleneck phase one has**: the root's TOR still serialises \|G\|-1
packets out of its uplinks. The expected plot would look identical
to phase one. Rejected.

(γ) is a two-level special case of (β). Simpler but adds no
structural benefit.

**Recommended: (β) tree replication.** Each switch along the tree
emits one packet per downstream branch. This is what gives the
constant-time completion-time curve the thesis wants to compare
against the baseline. It is also how real hardware multicast
works, so the simulator remains a faithful model.

### 3.2 How does a packet signal "I need multicast fanout"?

**Three candidates.**

- **(i) New `Packet::ptype` value**, e.g.\ `UEC_MCAST`. Switch
  branches on type before FIB lookup.
- **(ii) Reserved destination-address range.** Multicast group
  identifiers live in a disjoint subrange of `_dst` (e.g.\ the
  high bit); the FIB has entries keyed on those values.
- **(iii) Flag on the packet**, checked before FIB lookup.

(i) and (iii) require every switch site to check an extra field
and branch. (ii) drops into the existing
`_fib->getRoutes(pkt.dst())` path without any ingress-side
changes: the lookup returns a distinguished `FibEntry` (or a
flagged `vector<FibEntry*>`) that the switch interprets as
"fanout, not ECMP".

**Recommended: (ii) reserved destination range.** Define
`MCAST_BASE = 0x80000000` (or `topology_node_count` + offset) and
synthesise group identifiers
`mcast_dst(group_root, group_idx) = MCAST_BASE | ...`. The FIB
lookup path stays as-is; only the lookup *result* needs a new
interpretation.

### 3.3 FIB representation for multicast

**Three candidates.**

- **(p) Extend `FibEntry` with `vector<Route*>`** — one entry
  carries all egress ports.
- **(q) New `McastFibEntry : FibEntry`** that declares itself as a
  fanout entry and carries N `Route*`s.
- **(r) Reuse `vector<FibEntry*>`, mark it multicast.** For mcast
  destinations, `getRoutes()` returns the same shape as for ECMP
  but the switch interprets the vector differently: instead of
  picking one, it uses *all* of them.

(r) is the smallest diff and preserves the existing lookup cost.
The signal that tells the switch "use all, not one" is simply the
destination being in the mcast range (§3.2). Rejected as slightly
type-unsafe: a regular ECMP vector is easy to accidentally
multicast.

(q) is the cleanest. The subclass makes the semantic explicit and
keeps the interpreter free of ambient rules.

**Recommended: (q) `McastFibEntry : FibEntry`**, with
`getRoutes()` returning `vector<FibEntry*>` unchanged. On a
multicast destination the vector contains one `McastFibEntry`
(holding N egress `Route*`s) rather than several `FibEntry`s.
`FatTreeSwitch::getNextHop` detects the subclass and fans out.

### 3.4 Packet replication mechanism

**Two candidates.**

- **(u) Ref-count sharing.** Call `inc_ref_count(N-1)` on the
  arriving packet and queue the same pointer on N egress ports.
- **(v) Distinct copies via `UecPacket::newpkt(src)`.** Spawn
  N-1 fresh packets from the PacketDB pool, reusing the source's
  metadata, then free the original if all outputs are copies.

(u) is simpler but breaks because path state (`_route`,
`_pathid`, `_direction`) must differ per replica (§2.4).

**Recommended: (v) distinct copies.** The switch calls
`UecPacket::newpkt(*src)` once per egress beyond the first,
rewriting `_pathid` per copy (to give each branch independent
ECMP entropy upstream if any), keeping `_dst` as the multicast
group id (so downstream switches also fan out), and forwarding
the original packet along one of the branches to avoid a
redundant allocation.

### 3.5 Leaf-TOR delivery to hosts

At the last TOR in the tree, the multicast packet must be
delivered to every group-member host attached to that TOR. The
sinks were registered via `addHostPort(host, flow_id, endpoint)`
with *the host's own address*, not the mcast id.

**Three candidates.**

- **(x) Rewrite `_dst` to each host address at the leaf TOR**
  before emitting onto the host downlink.
- **(y) Install per-host `McastFibEntry` egress routes whose last
  hop is the host queue itself.** `addHostPort` still registers
  the sink; the mcast FIB at the leaf TOR maps
  `(group_id, host)` to that same host egress route.
- **(z) Introduce a new "mcast-aware" sink** that accepts packets
  with `_dst = mcast_id` and matches by `flow_id`.

(z) reaches furthest because it requires wiring the ToR to a new
dispatch path for multicast-dst packets. Rejected.

(x) is minimal: at the leaf TOR, when the fanout resolves, each
emitted replica's `_dst` is rewritten to the target host address,
so the existing host-fib machinery routes it the last hop
unchanged. Clean.

**Recommended: (x) rewrite `_dst` per host at the leaf TOR.** The
leaf TOR's multicast FIB entry carries, for each local group
member, the (host address, flow_id, host egress route); the
switch uses each tuple to produce a replica with
`_dst = host_addr` and `_flow_id = leg_flow_id`. Downstream of
the leaf TOR, nothing is new: packets look exactly like phase-one
unicast legs and the existing `UecBcastSink` handles them.

### 3.6 Which (root, group) pairs get a tree?

The `.cm` may contain several `start_bcast` entries; each pair
`(root, group_idx)` might be unique or repeated. Two options:

- **(m) One tree per group**, root-agnostic. A tree rooted
  anywhere in the group covers all members.
- **(n) One tree per (root, group_idx) pair.** Tighter but may
  duplicate.

Tree shape depends on root (interior-switch egress-port sets
differ). Rejected (m).

**Recommended: (n) one tree per distinct (root, group_idx).**
`set_up_mcast` walks `conns->connections` once, collects the set
of `(root, group_idx)` pairs from `is_bcast` entries, and
installs one mcast FIB per pair.

### 3.7 Naming & transport-class decomposition

Phase one kept the collective layer `bcast` and the network layer
`mcast` distinct. Phase two implements the network layer; the
collective endpoint changes too (one `UecBcastSrc` instead of
\|G\|-1, and it emits to the mcast destination). Two options:

- **(σ) Reuse `UecBcastSrc`** with a mode flag: if a topology has
  multicast installed for the op, emit one packet; otherwise emit
  \|G\|-1.
- **(τ) Dedicated `UecBcastSrcMcast` class** for the single-packet
  path; keep the phase-one class as the baseline.

For direct comparability of the two strategies in the thesis
plot, both must be runnable side-by-side selectable at the driver
level. This argues for two classes.

**Recommended: (τ) new `UecBcastSrcMcast`.** A new CLI flag
`-bcast_mode {baseline,mcast}` (default `baseline`) picks which
class is instantiated in the `is_bcast` branch of `main_uec.cpp`.
The completion barrier, the sinks, the recorder, and the
benchmark harness are unchanged.

## 4. Chosen Architecture (subject to approval)

Stitching the recommendations together:

1. **Source.** `UecBcastSrcMcast : public UecSrc` (new class in
   `uec_bcast.{h,cpp}`) emits exactly one packet per `.cm`
   broadcast entry. `_dst` is set to
   `mcast_dst(root, group_idx)`.
2. **FIB.** `McastFibEntry : public FibEntry` (new class in
   `routetable.{h,cpp}`) holds a `vector<Route*>` of egress
   routes and — for leaf TORs — per-host rewrite tuples
   `(host_addr, flow_id, leaf_route)`.
3. **Switch.** `FatTreeSwitch::getNextHop` detects an
   `McastFibEntry` and returns early; `receivePacket` then fans
   out: forward the original on the first branch, spawn N-1
   copies via `UecPacket::newpkt(src)` for the rest, rewriting
   `_dst`/`_flow_id` at the leaf TOR.
4. **Topology setup.** `FatTreeTopology::set_up_mcast` walks
   `conns` for `(root, group_idx)` pairs, builds a minimum
   replication tree per pair (see §3.1 + §2.2), installs an
   `McastFibEntry` on each switch on the tree.
5. **Sinks and barrier.** Unchanged. Still
   `UecBcastSink` per group member, still one `BarrierTrigger`
   with `count = |G|-1`, still the `BcastCompletionRecorder`
   producing `BCAST_COMPLETE ...` lines.
6. **Driver.** New `-bcast_mode {baseline,mcast}` CLI flag on
   `htsim_uec`. In the `is_bcast` branch of `main_uec.cpp`:
   - `baseline` (default): current \|G\|-1-leg path.
   - `mcast`: allocate one `UecBcastSrcMcast`; register it at
     the root's TOR under `flow_id` = op-level id; at each group
     member TOR, register a `UecBcastSink` under a per-member
     `leg_flow_id` (so the leaf-TOR fanout can rewrite `_dst` to
     the host and `_flow_id` to that leg id).

Benchmark harness (`gen_bcast_sweep.py`, `run_bcast_sweep.py`,
`plot_bcast_baseline.py`) is carried over. The plotter gains a
second line per topology for the `mcast` curve; the x- and y-axes
are identical so the two lines are directly comparable.

## 5. Implementation Plan

Ordered so each step is independently testable.

1. **Multicast address space** (small, isolated).
   - Add `mcast_dst(root, group_idx) -> uint32_t` helper in
     `uec_bcast.h`.
   - Add `Packet::is_mcast()` (range check on `_dst`).
   - Unit test: round-trip encode/decode.

2. **`McastFibEntry`** (small, no behavioural change).
   - New class in `routetable.{h,cpp}`; holds
     `vector<Route*>` and optional per-host rewrite table for
     leaf-TOR use.
   - Does not yet appear in any FIB.

3. **`FatTreeSwitch` fanout path** (focused diff).
   - In `getNextHop`: if the FIB vector contains an
     `McastFibEntry`, skip ECMP selection and return it as-is.
   - In `receivePacket` egress branch: if the attached route is
     from an `McastFibEntry`, iterate all branches, produce
     replicas via `UecPacket::newpkt(src)`, set
     `_route`/`_pathid`/`_nexthop` per branch, and at leaf TORs
     additionally rewrite `_dst`/`_flow_id` from the
     per-host rewrite table.
   - Unit test: a hand-constructed topology + hand-installed
     `McastFibEntry` fans out correctly (two fake hosts, one
     packet in, two packets out with correct dst).

4. **Tree construction** (logic, no switch changes).
   - New helper `FatTreeTopology::build_mcast_tree(root, group)`
     returning a list of per-switch `(switch_ptr, egress_routes,
     leaf_host_rewrites)` tuples.
   - Reference algorithm: for each destination `d ∈ group \
     {root}`, compute `path(root, d)` using the existing TOR /
     AGG / CORE hierarchy (up → Core if cross-pod, down from
     there); union the per-switch egress sets; record leaf-TOR
     host rewrites.
   - Unit test: K=4 fat-tree, group spanning two pods, check the
     tree has the expected six switches and the expected egress
     sets.

5. **`FatTreeTopology::set_up_mcast` body**.
   - Walk `conns` for `is_bcast` entries; collect
     `(root, group_idx)` pairs into a set; for each pair, call
     `build_mcast_tree` and install `McastFibEntry` entries on
     each switch along the tree, keyed by
     `mcast_dst(root, group_idx)`.
   - Fail with a clear message if a group member is unreachable
     (shouldn't happen in a complete fat-tree, but safety).

6. **`UecBcastSrcMcast`**.
   - New subclass in `uec_bcast.{h,cpp}`. `bcast_send_once`
     emits exactly one packet with `_dst = mcast_dst(...)` and
     the op-level `flow_id`.
   - Does NOT touch existing `UecBcastSrc`.

7. **Driver integration**.
   - Add `-bcast_mode {baseline,mcast}` flag.
   - Refactor the `is_bcast` branch to dispatch on mode. In
     `mcast` mode: allocate one source instead of \|G\|-1;
     register source at root's TOR under op-level `flow_id`;
     still register \|G\|-1 sinks at member TORs under
     per-leg `flow_id`s (so the final-TOR rewrite path can
     deliver to them).

8. **Benchmark extension**.
   - Extend `run_bcast_sweep.py` with a `--mode` argument that
     forwards `-bcast_mode` to `htsim_uec`; rerun the sweep for
     both modes and tag rows in the CSV with the mode.
   - Extend `plot_bcast_baseline.py` to draw one line per
     (topology, mode) pair.

9. **Thesis doc updates** (documentation, no code).
   - Add a new section to `AA-thesis-baseline.md` (or a
     companion `AA-thesis-phase2.md`) recording the design
     decisions made here.
   - Populate `thesis/Design and Implementation.tex` §INC
     Primitives, §Switch-Side Group Management with the
     implemented mechanism; add a phase-two `\includegraphics`
     and analysis in `thesis/Validation and Evaluation.tex`.

10. **Regression check**.
    - Re-run `bcast_test1.cm` (default `baseline` mode) and
      confirm outputs are bit-identical to the pre-phase-two
      run. Then run the same matrix with `-bcast_mode mcast` and
      confirm the completion time is dominated by path latency,
      not by \|G\|·serialisation.

Estimated complexity: steps 1–2 are small (≤ 1 day). Step 3 is
moderate (packet replication is subtle). Step 4 is the main new
algorithmic content (≤ 1 day for fat-tree). Step 5 is glue.
Steps 6–7 are ≤ 1 day combined. Steps 8–10 are documentation.

## 6. Benchmark and Expected Outcome

Sweep parameters match phase one (3 fat-trees × up to 10 group
sizes × 10 reps × 4 KB payload × 100 Gbps). With
`-bcast_mode mcast`, the expected completion-time curve is:

- **Constant in \|G\|** to within the spread of group-membership
  path lengths. The root emits one packet; fabric replication
  turns that into \|G\|-1 deliveries whose completion is the
  *max* of per-leaf path latencies, not a sum.
- **Sensitive to group *layout*.** Unlike phase one, where
  root-serialisation masked path effects, phase two's completion
  is exactly the slowest leaf's path latency. Intra-pod groups
  finish faster than cross-pod groups. Variance across reps
  should now be visible.
- **Topology size matters (slightly).** Larger fat-trees have
  more hops per cross-pod path, so the curves will separate
  slightly, unlike in phase one where they overlapped.

If the measured curve is *not* roughly constant in \|G\|, that is
a bug: something along the mcast path is still serialising.

## 7. Risks and Open Questions

- **Concurrent broadcasts sharing links.** Phase-two replication
  places multiple replicas on shared interior links. Under
  heavy offered load the root's uplink is no longer the
  bottleneck, but interior AGG/CORE uplinks might become one.
  Phase-two measurements with a single broadcast in isolation
  are cleanest first.
- **Packet identity in tracing.** `_packets` at each switch keys
  on a packet pointer; the fanout path introduces N distinct
  pointers at a switch. Need to confirm the tracking map works
  for all of them. Unit test covers this.
- **Interaction with ECMP upstream.** An AGG that receives a
  multicast packet and needs to fan out to, say, three TORs will
  pick one route per branch. If ECMP picks the same CORE for two
  branches, we get unnecessary serialisation on that CORE's
  downlink. Branch-specific `_pathid` values mitigate this;
  worth validating in the unit test.
- **`main_uec.cpp` already allocates a root-side `UecSrc`
  anyway.** In mcast mode the root-side object is just one
  instead of \|G\|-1, which is cheaper. Not a risk, just noting.
- **Does the driver's `-seed` matter now?** Under mcast,
  interior ECMP choices influenced by the branch-specific
  `_pathid` values can use `random()`; need to check whether
  the mcast path calls into `random()` anywhere.
- **Potentially required: `MCAST_BASE` safety vs.
  topology node count.** Choose `MCAST_BASE` so that it is
  unambiguously above any possible host id
  (`topology->no_of_nodes()` returns the bound we need). Assert
  at `set_up_mcast` start.

## 8. Non-Goals for Phase Two

- Other collectives (Scatter, Gather, Reduce, Allreduce). Their
  switch-level primitives will share the group-FIB mechanism
  introduced here but their send/completion logic differs. Out
  of scope.
- Congestion control and trimming on multicast packets.
  Assumption (A3) (infinite switch buffers) remains in effect.
  Real-hardware multicast interacts with backpressure in a
  specific way; that is its own sub-project.
- Multi-root or any-to-all schedules. Phase two stays single-root
  per operation.
- Failure injection on multicast paths. The `failure` machinery
  in `ConnectionMatrix` is orthogonal.
- Packet-format changes beyond adding a "this is multicast" bit
  (via `_dst` range).
