# Phase-Two Plan v3 — Switch-Level INC Replication, Designed for the Full Collective Family

*Proposal v3. Supersedes `v2.md` on §3.3, §3.6, §4,
§5, and adds a new §10 that previews how phase three (aggregation)
and the higher-grade collectives (Allreduce, Allgather) reuse the
phase-two FIB shape. The (β) tree replication choice (§3.1) and
the (m')/RPF dispatch model (§3.6) are unchanged from v2 — the
design rationale is now framed around the **full INC scope from
the thesis proposal**, not multicast in isolation.*

*Three concrete changes from v2:*
1. *FIB-entry class renamed `McastFibEntry` → `INCFibEntry`,
   shaped as a 128-bit port bitmap + sparse leaf-TOR rewrite map.*
2. *§3.6 rationale rewritten to lead with Allgather/Allreduce
   structural necessity. ASIC fidelity is now a secondary win.*
3. *New §10 demonstrates that aggregation, Allreduce, and Allgather
   reuse this exact FIB representation with small additive
   extensions in phase three — validating the v3 design forward.*

*No code has been written. Please approve, amend, or reject.*

## 0. What Changed Relative to v2

| Aspect | v2 | v3 |
|---|---|---|
| FIB-entry class name | `McastFibEntry` | `INCFibEntry` (multicast-only fields populated in phase two; aggregation fields added in phase three) |
| Tree-port representation | `vector<TreePort>` with `Route* egress`, `BaseQueue* port_queue`, `optional<int> rewrite_dst` per entry | `std::bitset<128> tree_port_mask` + sparse `vector<pair<uint8_t,int>> host_rewrites` |
| Memory per entry (avg) | ~128 bytes | ~16 bytes + sparse rewrites |
| Storage scaling | Linear in tree size | Constant in tree size (bitmap), sparse rewrites only at leaf TORs |
| Egress route construction | Pre-baked per `TreePort` | Cached once at switch init; indexed by port |
| §3.6 rationale framing | "Architectural fidelity to ASIC" (primary) | "Structurally necessary for Allgather/Allreduce" (primary); ASIC fidelity (secondary) |
| Phase-3 reuse claim | Implicit | Explicit §10 with reduce/allreduce/allgather walk-throughs |

**Why these changes**: the thesis proposal
(`INC_thesis_proposal.md`) targets grade 5.25 — Allgather and
Allreduce on top of in-network multicast and aggregation. v2's
`vector<TreePort>` shape works for multicast in isolation but
doesn't compose cleanly with aggregation's input-port-mask
operations or with Allreduce's two-phase reduce-up-then-multicast-
down dispatch. The bitmap shape is the SHARP/Tomahawk multicast-
table representation and naturally extends to all four operations
in the thesis scope. Choosing it now in phase two means phase
three (aggregation) reuses the FIB infrastructure rather than
rewriting it.

## 1. Recap: Phase Map and Thesis Context

The thesis proposal defines four INC implementation deliverables
(§3 of `INC_thesis_proposal.md`):

1. Multicast/aggregation tree creation across switches.
2. Multicast/aggregation packet-format support in htsim.
3. Multicast/aggregation group management on switches (FIB).
4. Switch-side execution: replication and **payload aggregation**.

Mapped to phases:

| Phase | Scope | Status | Grade tier reached |
|---|---|---|---|
| Phase 1 | P2P unicast broadcast baseline | merged (`WIP-multicast-htsim-direct`) | grade 4.0 floor |
| **Phase 2** (this plan) | Switch-level multicast tree + RPF dispatch + INCFibEntry foundation | **in design** | grade 4.0 / 5.0 (Bcast on multicast) |
| Phase 3 | Aggregation primitive + Reduce + Allreduce + Allgather; packet-format extensions | future | grade 5.0 / 5.25 |
| Phase 4 | Validation, analysis, upstreaming | future | grade 5.75 / 6.0 |

Phase 1 emulates `MPI_Bcast` by decomposing one broadcast into
\|G\|-1 ACK-less unicast legs. The root's uplink serialises the
legs and produces a linear completion-time curve (≈339 ns per
added leg, Chapter 4.3 of the thesis draft).

**Phase two introduces the switch-level multicast mechanism**: the
root emits one packet, the fabric replicates it via tree
replication and RPF dispatch, and \|G\|-1 deliveries arrive in
parallel. The completion-time curve becomes constant in \|G\|,
dominated by the worst leaf-path latency.

The phase-one benchmark harness, sink, and barrier orchestration
carry over **unchanged**. Only the sending endpoint and the
fabric-internal routing change.

## 2. Ground Truth from the Codebase

### 2.1 Switch forwarding is two-stage and strictly unicast

`FatTreeSwitch::receivePacket` (`fat_tree_switch.cpp:23`) runs a
two-step pipeline per packet: ingress (FIB lookup, route attach,
pipe delay) then egress (sendOn). The FIB is destination-keyed:
`RouteTable::_fib : unordered_map<int, vector<FibEntry*>*>`
(`routetable.h:52`). For unicast, the vector is the ECMP
alternatives list; `getNextHop` picks one via `freeBSDHash(flow_id,
pathid, salt)`.

Packets carry single-path state (`_dst`, `_pathid`, `_route`,
`_nexthop`, `_direction`) and take exactly one route per hop.
**No code path anywhere in htsim fans a single packet to multiple
egress ports today.**

`getNextHop(Packet&, BaseQueue* ingress_port)` already accepts an
ingress argument but `receivePacket` calls it with `NULL`
(`fat_tree_switch.cpp:44`). v3's RPF dispatch threads the actual
ingress through.

### 2.2 `FatTreeTopology::set_up_mcast` is a stub, correctly placed

Defined at `fat_tree_topology.cpp:596`, called from
`main_uec.cpp:781` after topology construction and `conns->groups`
attachment but before per-flow source/sink instantiation. Under
v3 this ordering is **load-bearing and correct** — per-group tree
construction depends only on group membership and topology, not
on sink objects.

The topology exposes everything needed for tree construction:
`switches_lp / switches_up / switches_c`, `queues_*` and `pipes_*`
indexed by `[from_tier][to_tier][bundle]`, `HOST_POD_SWITCH(host)`,
`MIN_POD_AGG_SWITCH(pod)`, `MAX_POD_AGG_SWITCH(pod)`,
`AGG_SWITCH_POD_ID(agg)`, `tor_switches_per_pod()`,
`agg_switches_per_pod()`, `bundlesize(tier)`.

### 2.3 Packet refcount exists but cannot be used for fanout

`PacketDB::inc_ref_count`/`dec_ref_count` (`network.h:164–166`)
plus the freelist (`network.h:299–305`) would in principle allow
shared-pointer fanout. **It doesn't work** because `Packet` fuses
body and per-recipient state (`_route`, `_pathid`, `_nexthop`,
`_direction`, `_dst`) into one object. Real ASICs separate body
(shared SRAM cell, refcounted) from descriptor (per-egress
metadata); htsim doesn't, so each replica must be its own
`Packet`. v3 keeps v2's recommendation: distinct copies via a new
`UecPacket::newpkt_replica` factory.

### 2.4 No pre-existing multicast or aggregation anywhere

Searched all transports (`uec.cpp`, `eqds.cpp`, `ndp.cpp`,
`tcp.cpp`, `roce.cpp`, `swift.cpp`, `hpcc.cpp`, `strack.cpp`,
`switch.cpp`, queue types, tests). No replication, fanout, or
multicast routing outside the stub. **No reduction/aggregation
primitive of any kind.** Phase two and phase three are both
from-scratch extensions.

### 2.5 The collective-input format (`.cm`) accepts `start_bcast` only

`connection_matrix.cpp:761` parses `start_bcast`; line 967–983
asserts that `.cm` files using collective ops require explicit
`id` on every connection. **No `start_reduce`, `start_allreduce`,
`start_allgather` tokens exist yet.** Phase three will add them
following the same parser pattern.

### 2.6 `Switch::_ports` provides stable port indices

`Switch::addPort` (`switch.cpp:12`) appends to `_ports` and returns
the new index. Each queue gets `setSwitch(this)`, so `q->getSwitch()`
gives reverse identification. `Switch::getPort(i)` retrieves by
index. **Port indices are stable for the lifetime of the
simulation** because `_ports` is populated once at topology init
and never modified.

`fat_tree_topology.cpp:798, 859, 860, 935, 936` populates `_ports`
for every switch tier and asserts:

```c
assert(switches_lp[tor]->addPort(...) < 96);   // TOR: ≤ 96 ports
assert(switches_up[agg]->addPort(...) < 64);   // AGG: ≤ 64 ports
assert(switches_c[core]->addPort(...) < 64);   // CORE: ≤ 64 ports
```

**Implication for FIB representation**: port indices fit in
`uint8_t` comfortably. The bitmap representation must accommodate
up to 96 bits — `uint64_t` is insufficient. v3 uses
`std::bitset<128>` to give margin without overcommitting.

### 2.7 `Packet::ptype` and packet format extensibility

`Packet` (`network.h:83–226`) is the base class; transport-
specific subclasses (`UecPacket`, `NdpPacket`, etc.) add their
own fields. The proposal's deliverable §3.2 ("integrating
multicast/aggregation metadata support into the HTSIM packet
format") implies phase three will need new packet fields:
operation type (multicast vs reduce vs allreduce phase),
operation sequence number (to disambiguate concurrent
aggregations on the same group), partial-reduction state (small
operand carried alongside the body).

**Phase two does not need any of this.** Multicast can be
signalled via the §3.2 dst-range encoding alone. v3 flags the
phase-three packet-format work as a known follow-up but doesn't
prescribe it.

### 2.8 Consequence for the v3 design

The cleanest insertion point remains
`FatTreeSwitch::getNextHop` + `FatTreeSwitch::receivePacket`:
teach them that destinations in the multicast range mean "fan me
out to all tree ports except the ingress, computed via bitmap
intersection." The `INCFibEntry` class is the foundation for
phase-three aggregation entries; phase two populates only the
multicast-relevant fields.

## 3. Design Decisions

### 3.1 Where does replication happen?

*(Unchanged from v2.)* **Recommended: (β) tree replication.**
Each switch on the multicast tree emits one packet per non-ingress
tree port. This produces the constant-in-\|G\| completion-time
curve and matches real hardware (NVIDIA SHARP, Broadcom Scorpion).

### 3.2 How does a packet signal "I need multicast fanout"?

*(Unchanged from v2.)* **Recommended: (ii) reserved destination
range.** Define `MCAST_BASE = 0x80000000` and synthesise group
identifiers `mcast_dst(group_idx) = MCAST_BASE | group_idx`.
Assert `MCAST_BASE > topology->no_of_nodes()` at `set_up_mcast`
start.

**Forward-looking note**: phase three will need to distinguish
multicast packets from aggregation packets on the same `_dst`
(both reference the same group). Three options for phase three
(deferred to that scoping):

- Reuse the dst encoding by partitioning the high bits:
  `inc_dst(op_type, group_idx) = INC_BASE | (op_type << 28) | group_idx`.
- Add an operation-type field to the packet header (cleanest;
  matches the proposal's "packet-format updates" deliverable).
- Use `Packet::ptype` (e.g., new `UEC_MCAST`, `UEC_REDUCE`
  variants).

Phase two does not need any operation-type signalling because
multicast is the only operation. The decision is flagged as a
**phase-three open question** in §10.

### 3.3 FIB representation — **the v3 change**

**Three candidates** revisited in light of the full INC scope:

- **(A) `vector<TreePort>` with explicit `Route*` per port.** v2's
  recommendation. Stores ~128 bytes per FIB entry on average; one
  struct per tree-member port; pre-baked routes per port.
- **(B) `vector<TreePort>` with port indices (uint8_t).** Slimmer
  than A; same vector-of-struct shape but smaller fields.
- **(C) Port bitmap (`std::bitset<128>`) + sparse rewrite map.**
  Matches ASIC multicast-table representation. ~16 bytes per FIB
  entry; bit operations for dispatch; small parallel structure
  for leaf-TOR rewrites.

**Recommended: (C) port bitmap.** Class shape:

```c
class INCFibEntry : public FibEntry {
public:
    // Multicast tree: bit i set ↔ Switch::_ports[i] is in this group's
    // tree at this switch. Used by:
    //   - Multicast / Allgather dispatch: replicate to (mask & ~ingress).
    //   - Aggregation / Reduce: input ports = (mask & ~root_port_idx).
    //   - Allreduce: tree_port_mask serves both phases.
    std::bitset<128> tree_port_mask;

    // PHASE 3 ONLY: which port leads "toward root" for a reduce-
    // direction op. nullopt at the root switch and at switches
    // not participating in reduce ops. Set at install time per
    // (group, reduce-root) pair.
    std::optional<uint8_t> root_port_idx;

    // Leaf-TOR per-host rewrites: which host_addr each member
    // port rewrites _dst to. Sparse — typically 1–8 entries per
    // group at a leaf TOR; empty at interior switches.
    std::vector<std::pair<uint8_t, int>> host_rewrites;

    // Defensive override against legacy ECMP code paths.
    Route* getEgressPort() override {
        assert(0 && "INCFibEntry has fanout/aggregation semantics; "
                    "use tree_port_mask + Switch::_ports");
        return nullptr;
    }

    // Helper for dispatch:
    std::optional<int> rewrite_for(uint8_t port_idx) const {
        for (auto& [idx, host] : host_rewrites)
            if (idx == port_idx) return host;
        return std::nullopt;
    }
};
```

#### Why (C) over (A) and (B)

For phase two in isolation, all three options work and storage
differences are immaterial at thesis scale. The decision is
forced by **phase-three requirements**:

1. **Aggregation** at a switch needs a port mask (which downstream
   ports we expect packets from) plus a counter (how many
   arrived). The mask shape is exactly `std::bitset<N>`. With
   (A)/(B), aggregation would store a parallel mask alongside
   the route-vector — two structures to keep in sync.
   With (C), the multicast `tree_port_mask` *is* the aggregation
   input mask (modulo `root_port_idx` exclusion). One source of
   truth.

2. **Allreduce** is reduce-up-then-multicast-down on the same
   tree. With (C), the same `INCFibEntry` serves both phases —
   the dispatch code differs but the FIB state is shared. With
   (A)/(B), you'd have two parallel data structures (a route
   vector for multicast and a mask for aggregation) at every
   switch, both per group — twice the state, twice the
   synchronization risk.

3. **Allgather** is |G| pipelined broadcasts on the same per-group
   tree. The FIB doesn't change at all between operations; only
   the orchestration layer (ConnectionMatrix / driver) schedules
   |G| broadcasts. (C) makes this trivial. (A)/(B) work too but
   require iterating tree ports per replica, which doesn't
   compose with the aggregation phase if Allgather later wants
   to be expressed as Allreduce-with-concat.

4. **Set operations**: phase three may need to compose tree-
   member sets (e.g., to compute "ports active in this op's
   sub-tree"). Bit operations (AND, OR, XOR, popcount,
   find-first-set) are O(1)–O(128/word). Vector operations are
   O(N) and don't compose as cleanly.

The (C) representation matches NVIDIA SHARP's multicast-table
shape and Broadcom Tomahawk's multicast group descriptor. The
storage savings are nice but secondary; the **compositional
benefit for phase three** is what makes (C) the right call now
rather than later.

#### Trade-offs and mitigations

**Concern**: ingress-port identification needs to map upstream
queue → port index at this switch. Mitigation: cache a
`unordered_map<BaseQueue*, uint8_t>` at switch construction
time, populated alongside `_ports`. O(1) lookup at dispatch.

**Concern**: leaf-TOR `tree_port_mask` and `host_rewrites` are
two structures that must stay synchronized — set bit i in mask
must imply some entry exists in rewrites if i corresponds to a
host port. Mitigation: define the invariant explicitly and assert
it once at the end of `set_up_mcast`:

```c
for (size_t i = mask._Find_first(); i < 128; i = mask._Find_next(i)) {
    if (is_host_downlink_port(this_switch, i)) {
        assert(entry->rewrite_for(i).has_value() &&
               "leaf-TOR member port missing host rewrite");
    }
}
```

Convert silent-wrong into loud-fail at install time.

**Concern**: bit-iteration via `_Find_first`/`_Find_next` is
libstdc++-specific. Mitigation: portable equivalent:

```c
for (size_t i = 0; i < 128; ++i) {
    if (!mask.test(i)) continue;
    // ... use port i
}
```

For 128-bit masks the linear scan is ~30ns wall-clock — invisible
in simulation cost.

### 3.4 Packet replication mechanism

*(Unchanged from v2: distinct copies via a new
`UecPacket::newpkt_replica` factory. The existing `newpkt(source)`
sets `size = acksize` and copies the source's route, both wrong
for full-data fanout.)*

Dispatch loop under (C):

```c
auto* m = dynamic_cast<INCFibEntry*>(entry);
if (m) {
    uint8_t ingress_idx = identify_ingress_port_idx(pkt);
    std::bitset<128> egress_mask = m->tree_port_mask;
    egress_mask.reset(ingress_idx);

    for (size_t i = 0; i < 128; ++i) {
        if (!egress_mask.test(i)) continue;
        BaseQueue* q = _ports[i];
        Route* egress = _port_egress_routes[i];   // cached at switch init
        int dst = m->rewrite_for(i).value_or(pkt.dst());
        UecPacket* replica = UecPacket::newpkt_replica(
            *static_cast<UecPacket*>(&pkt),
            *egress, dst, /*pathid=*/pkt.pathid() + i);
        replica->set_direction(NONE);   // re-establish at next hop
        _packets[replica] = true;        // mark for egress branch
        _pipe->receivePacket(*replica);
    }
    pkt.free();   // symmetric: original is freed; all copies are fresh
    return;
}
```

The `_port_egress_routes` cache is populated once at switch
construction:

```c
// In FatTreeSwitch constructor or init:
_port_egress_routes.resize(_ports.size());
for (size_t i = 0; i < _ports.size(); ++i) {
    Route* r = new Route();
    r->push_back(_ports[i]);                       // egress queue
    r->push_back(get_pipe_for_port(_ports[i]));    // companion pipe
    r->push_back(_ports[i]->getRemoteEndpoint());  // next-hop entity
    _port_egress_routes[i] = r;
}
```

`get_pipe_for_port` is a small helper that maps from queue back to
the parallel pipe (the topology arrays already pair them; can be
done by index if `_ports` is populated in a known order, or via a
parallel `_port_pipes` map populated at the same time as `_ports`).

**Note on `_pathid`**: setting per-replica `_pathid = source_pathid
+ branch_idx` is purely cosmetic — under tree replication, neither
ECMP nor `_pathid` affects routing on the multicast path.
Distinguishable `_pathid` per replica makes traces easier to read.
v3 acknowledges this explicitly (v2 did, v1 misleadingly justified
it as "ECMP entropy upstream").

### 3.5 Leaf-TOR delivery to hosts

*(Unchanged from v2.)* **Recommended: (x) rewrite `_dst` per host
at the leaf TOR.** No `_flow_id` rewrite — sinks register under
op-level `flow_id` directly because `(host_addr, op_flow_id)` is
already unique across concurrent operations.

Implementation: when the dispatch loop hits a tree-port whose
`m->rewrite_for(i)` is set, the replica's `_dst` becomes
`host_addr`. The replica then re-enters `getNextHop`, which falls
into the existing host-fib lookup path (`_fib->getHostRoute(host,
flow_id)`) and returns the route to the registered sink. Standard
unicast handling resumes.

### 3.6 Tree granularity — **the v3 rationale rewrite**

**Three candidates** *(unchanged from v2; rationale rewritten)*:

- **(m) One static directed tree per group.** Rejected: directed
  egress lists depend on source.
- **(n) One tree per (root, group_idx).** Rejected — see below.
- **(m') One undirected tree per group with RPF dispatch.**
  Recommended.

**Recommended: (m') one undirected tree per group, RPF dispatch.**

#### Primary rationale: structural necessity for grade 5.25

The thesis proposal targets grade 5.25, which requires Allgather
and Allreduce. Under (n) "one tree per (root, group)":

- **Allgather** has |G| sources per group, each potentially
  needing its own per-(source, group) tree. State explodes to
  O(|G|² × topology_size) FIB entries.
- **Allreduce**, implemented as reduce-up-then-multicast-down,
  needs the multicast-down phase to deliver to every member from
  the reduction root. Under (n) this is per-(root, group) state
  and can't be shared with the Bcast trees from other roots.

Under (m'):

- **Allgather** is |G| pipelined broadcasts on the **same**
  per-group tree. The FIB doesn't change between operations; only
  the orchestration layer schedules them.
- **Allreduce** uses the same per-group tree for both phases:
  reduce-up uses the mask with `root_port_idx` exclusion;
  multicast-down uses the mask with ingress exclusion.

So the structural reasoning for (m'): **per-(source, group) FIB
state cannot scale to the higher-grade collectives in the thesis
scope; per-group state can.** The phase-two design is forward-
load-bearing — choosing (n) now would force a representational
rewrite to reach grade 5.25.

#### Secondary rationale: architectural fidelity to ASIC multicast

Real switch ASICs (Broadcom Tomahawk multicast tables, NVIDIA
Spectrum, Cisco Silicon One) store multicast as **port bitmaps
keyed by group**, not directed routes keyed by (source, group).
Replication is a hardware fanout from the bitmap, with ingress
port masked out — pure RPF. (m') matches this model down to the
data structure (the bitset *is* the bitmap).

This argument matters for the thesis writeup: claiming "we model
switch-level multicast as in production hardware" is more
defensible when the simulator's FIB shape literally matches what
the ASIC stores.

#### What (m') costs

The tree-construction algorithm must produce a **root-agnostic,
acyclic, undirected tree** per group. Concretely: the same set of
switches and the same set of links must appear regardless of
which member sources. Achievable in fat-tree by deterministic
AGG/Core selection (see §5 step 4).

If the algorithm ever picks paths starting from a specific root
(e.g., ECMP-style hashing on root-flow-id), different sources see
different trees and "skip ingress" RPF fails. v3's algorithm
forecloses this by construction.

#### What v3 does **not** import from real-world multicast

We use the simplest form of RPF: skip ingress; otherwise replicate
to all tree-member ports. We do not implement:

- **Source-specific RPF check** (drop packets arriving on a non-
  toward-source port). Under assumption (A1) — single broadcast
  in isolation, no failures — there's no risk of misrouted
  packets.
- **Multi-source shared-tree with Rendezvous Point** (PIM-SM).
  Each group has one tree; any member can source.
- **Loop suppression beyond skip-ingress.** Trees are shortest-
  path subgraphs of the fat-tree, inherently acyclic.

Flagged as non-goals in §8.

*(Unchanged from v2: new `UecBcastSrcMcast` class, CLI flag

## 4. Chosen Architecture (subject to approval)

Stitching the v3 recommendations together:

1. **Source.** `UecBcastSrcMcast : public UecSrc` (new class in
   `uec_bcast.{h,cpp}`) emits exactly one packet per `.cm`
   broadcast entry. The source's `_flow` carries the op-level
   `flow_id`. `_dst = mcast_dst(group_idx)`.

2. **FIB.** `INCFibEntry : public FibEntry` (new class in
   `routetable.{h,cpp}`) holds:
   - `std::bitset<128> tree_port_mask` — populated in phase two.
   - `std::optional<uint8_t> root_port_idx` — phase three only;
     remains nullopt under phase-two-only installations.
   - `std::vector<std::pair<uint8_t, int>> host_rewrites` —
     populated at leaf TORs in phase two.
   - `getEgressPort()` overridden to assert (defensive against
     legacy ECMP code).

3. **Switch.**
   - Add `unordered_map<BaseQueue*, uint8_t> _port_idx_by_queue`
     to `FatTreeSwitch`, populated at construction alongside
     `_ports`.
   - Add `vector<Route*> _port_egress_routes`, populated once at
     switch init from `_ports`.
   - In `receivePacket`: identify the ingress queue via
     `pkt.route()->at(pkt.nexthop() - 2)` (the upstream queue
     just before this switch); look up its port index via
     `_port_idx_by_queue` of the **upstream switch**, OR more
     simply, identify by matching `_ports[i]->getRemoteEndpoint()`
     against the upstream switch.
   - In `getNextHop`: detect `INCFibEntry` and return it as-is.
   - In `receivePacket` ingress branch: if FIB returned an
     `INCFibEntry`, run the bitmap-based fanout dispatch (§3.4).

4. **Topology setup.** `FatTreeTopology::set_up_mcast` walks
   `conns->groups`. For each group_idx with `groups[idx].size()
   >= 2`:
   - Build a deterministic, root-agnostic, undirected tree
     (algorithm §5 step 4).
   - Install one `INCFibEntry` per switch on the tree, keyed by
     `mcast_dst(group_idx)`. Set `tree_port_mask` bits for tree-
     member ports; populate `host_rewrites` at leaf TORs;
     `root_port_idx` left nullopt (phase two doesn't use it).
   - Run the leaf-TOR consistency invariant assertion (§3.3).

5. **Sinks and barrier.** Unchanged from phase one. Sinks
   registered via `addHostPort(host_addr, op_flow_id, sink)` —
   op-level flow_id, no per-leg derivation.

6. **Driver.** New `-bcast_mode {baseline,mcast}` flag in
   `main_uec.cpp`. In `mcast` mode:
   - One `UecBcastSrcMcast` per `is_bcast` connection.
   - Source registered at root's TOR via `addHostPort(root,
     op_flow_id, src)`.
   - Each member ≠ root: `UecBcastSink` registered via
     `addHostPort(member, op_flow_id, sink)`.
   - BarrierTrigger and BcastCompletionRecorder unchanged from
     phase one.

The `next_bcast_leg_flow_id` machinery is removed in mcast mode
(retained for baseline).

## 5. Implementation Plan

Ordered for independent testability. Steps 1, 6, 8, 9, 10
unchanged from v2. Steps 2, 3, 4, 5, 7 differ at the data-
structure level.

1. **Multicast address space** *(small, isolated, ~2h)*.
   - Add `mcast_dst(group_idx) -> uint32_t` helper in

4. **Tree construction** *(main new algorithmic content, ~1
   day)*.
   - New helper `FatTreeTopology::build_mcast_tree(int
     group_idx)` returning per-switch `(switch_ptr,
     tree_port_idx_set, host_rewrites)`.
   - **Reference algorithm (root-agnostic, deterministic)**:
     ```
     members     = groups[group_idx]
     member_tors = { HOST_POD_SWITCH(h) for h in members }
     member_pods = { HOST_POD(h)        for h in members }

     # Same podpos in every relevant pod (AGG-Core compatibility):
     podpos      = group_idx % agg_switches_per_pod()

     for tor in member_tors:
         agg_in_pod = MIN_POD_AGG_SWITCH(HOST_POD of tor) + podpos
         tor's tree_port_idx_set:
             - For each member m on this TOR:
                 add port_idx(host_downlink to m); record (idx, m)
                 in host_rewrites
             - add port_idx(uplink to agg_in_pod)

     for pod in member_pods:
         agg = MIN_POD_AGG_SWITCH(pod) + podpos
         agg's tree_port_idx_set:
             - For each member_tor in this pod:
                 add port_idx(downlink to member_tor)
             - if multi-pod:
                 add port_idx(uplink to chosen_core)

     if len(member_pods) > 1:
         uplink_bundles = radix_up(AGG_TIER) / bundlesize(CORE_TIER)
         core_offset    = (group_idx / agg_switches_per_pod())
                          % uplink_bundles
         chosen_core    = core_offset * agg_switches_per_pod()
                          + podpos
         core's tree_port_idx_set:
             - For each pod in member_pods:
                 add port_idx(downlink to chosen AGG in that pod)
     ```
   - Edge cases: all members on one TOR (no AGG/Core); single-
     pod multi-TOR (no Core); 2-tier topology (no Core).
   - Invariant check: resulting per-switch port sets, viewed as
     undirected graph, form an acyclic tree. Add a
     `verify_tree_acyclic()` helper.
   - Unit tests: K=4 fat-tree, intra-TOR / intra-pod / cross-pod
     groups; for cross-pod, verify the same tree results from
     multiple sources (root-agnostic property check).

## 7. Risks and Open Questions

- **Concurrent broadcasts share interior tree links.** Under (m')
  more so than under (n), because per-group trees concentrate
  load on the single chosen Core/AGG per group. Phase-two
  measurements with one broadcast in isolation are cleanest
  first. If phase-three adds finite buffers, this matters.

- **Bitmap–rewrite synchronization.** `tree_port_mask` and
  `host_rewrites` must agree at leaf TORs. The post-install
  invariant assertion catches drift; new contributors must
  remember to keep the invariant. v3 asserts loudly; doesn't
  prevent construction-time mistakes.

- **Ingress port identification correctness.** Route inspection
  via `pkt.route()->at(nexthop - 2)` assumes the upstream queue
  is at that index — true for the standard 3-element route
  shape, may need verification for unusual shapes (e.g.,
  failure-rerouted paths). Property to assert in unit tests.

- **`_direction` state machine on replicas.** Each replica's
  `_direction` is reset to `NONE`; next switch establishes
  `UP`/`DOWN`. Fat-tree shortest-path trees never require
  `DOWN→UP` transitions, so the existing `Packet::set_direction`
  assert is satisfied by construction. Verify in unit test.

- **`MCAST_BASE` safety.** Assert `MCAST_BASE >
  topology->no_of_nodes()` at `set_up_mcast` start.

- **Phase-three dependency lock-in.** v3 commits to bitmap-based
  FIB shape under the assumption that aggregation will reuse it
  cleanly. If phase three discovers aggregation needs a
  fundamentally different shape (e.g., needs per-port priority
  ordering, per-port scheduling weight), some redesign is needed.
  Mitigation: §10 walks through aggregation/reduce/allreduce/
  allgather concretely, validating the shape before commit.

- **Time-budget pressure.** Proposal allocates 90h to weeks 4–8
  for *all* INC implementation: multicast (this phase, ~30–40h),
  aggregation, packet-format updates, collective integration,
  unit tests. Probable over-run. Implication: don't perfect
  phase-two cosmetic details (per-replica `_pathid`, branch-
  vs-original asymmetry) at the cost of phase-three progress.
  Get the FIB shape right; cut everything else to minimum-viable.

- **(Removed from v1 and v2)**: ECMP-picks-same-Core risk,
  set_up_mcast/sink-registration ordering — both eliminated by
  v2's design choices, kept eliminated in v3.

## 10. Phase 3 Preview: Aggregation, Reduce, Allreduce, Allgather on the v3 FIB

This section is **forward-looking**. It is not part of phase-two
deliverables. Its purpose: validate that the v3 FIB representation
extends cleanly to the higher-grade collectives, so that phase
two doesn't paint phase three into a corner.

### 10.1 Aggregation primitive at the switch

Aggregation in switches:

1. Receive multiple packets (one per downstream tree port).
2. Wait until all expected inputs arrive.
3. Reduce them via a designated operator (sum, min, max, etc.).
4. Forward one reduced packet upstream.

**FIB extension**: `INCFibEntry::root_port_idx` is set to the
single upstream port (the one leading toward the reduction root).
The aggregation input port set is `tree_port_mask & ~(1 <<
root_port_idx)`.

**Per-active-op state**: keyed by `(group_idx, op_seq_id)`, holds:
- Counter: how many inputs have arrived.
- Buffer: the partial reduction.
- Ack state.

Stored separately from the FIB (op state is short-lived; FIB is
long-lived). Likely a `unordered_map<pair<group_idx, op_seq_id>,
ReduceState*>` per switch.

**Dispatch sketch**:

```c
auto* m = dynamic_cast<INCFibEntry*>(entry);
uint8_t ingress_idx = identify_ingress_port_idx(pkt);

if (m && m->root_port_idx && /* op type == reduce */) {
    if (!m->tree_port_mask.test(ingress_idx) ||
        ingress_idx == *m->root_port_idx) {
        // Stray packet; drop.
        pkt.free(); return;
    }
    auto* state = lookup_or_create_state(group_idx, op_seq_id);
    state->aggregate(pkt);
    state->arrived++;
    pkt.free();   // input consumed

    size_t expected = m->tree_port_mask.count() - 1;
    if (state->arrived == expected) {
        UecReducePacket* out = build_reduced_packet(state);
        out->set_route(*_port_egress_routes[*m->root_port_idx]);
        _packets[out] = true;
        _pipe->receivePacket(*out);
        free_state(group_idx, op_seq_id);
    }
}
```

**Reuses from phase two**:
- `INCFibEntry` class (just adds `root_port_idx` semantics).
- Ingress port identification (`identify_ingress_port_idx`).
- Tree construction (`build_mcast_tree` — same per-group tree
  serves aggregation; just walk it differently).
- `_port_egress_routes` cache.
- `set_up_mcast` becomes `set_up_inc` (or extended) — for each
  group, also pre-compute `root_port_idx` per (group, reduction-
  root-host) pair if reduce ops exist on that group.

**New in phase three**:
- `UecReducePacket` (or similar) carrying partial-reduction state.
- Per-active-op reduction state map per switch.
- Reduction-operator implementations (sum/min/max/etc.).
- Driver branch for `start_reduce` connections.
- Operation-type signaling on packets (resolves §3.2's deferred
  question).

### 10.2 Reduce collective

Many-to-one reduction. One root host receives the aggregate.

- Each member host emits a packet with partial value.
- Tree converges: each AGG/Core aggregates downstream inputs
  into one upward packet.
- Root TOR receives the final packet and delivers to root host.

**FIB at each switch**: same as multicast tree (same
`tree_port_mask`). Addition: `root_port_idx` set to the port
leading to the next switch toward the root. At the root TOR,
`root_port_idx = nullopt`; the reduced packet is delivered via
host-fib lookup to the root host.

**`root_port_idx` is per (group, reduction-root-host)**, not per
group. So the FIB needs either:
- A small per-switch table mapping `reduction_root_host_id →
  root_port_idx`, OR
- A `vector<INCFibEntry*>` indexed by reduction root, with
  shared `tree_port_mask` and per-root `root_port_idx`.

The first is more compact (one bitmap + a small lookup table per
group). The second is simpler at dispatch time.

**Either way, the per-group tree is shared.** The "root direction"
state is small — at most 8 bits per (switch, group, root) — and
fits in a tiny per-switch sub-table.

### 10.3 Allreduce collective

Two phases on the same tree:

- **Phase A: Reduce up** — every member contributes; switches
  aggregate; one reduced packet reaches the (designated)
  reduction root.
- **Phase B: Multicast down** — the root sends the reduced value
  back; tree replicates to every member.

**FIB**: same `INCFibEntry` per group serves both phases:
- Phase A uses `tree_port_mask` minus `root_port_idx` as input
  set.
- Phase B uses `tree_port_mask` minus ingress (RPF) for fanout.

**Choice of root**: typically deterministic (e.g., lowest member
ID). Internal to the implementation; user doesn't pick.

**Operation-type signal on packets** distinguishes phase-A from
phase-B at the switch dispatch site. Phase A increments counters
and aggregates; phase B fans out.

The same FIB serves all four operations (multicast, reduce,
allreduce-up, allreduce-down) by switching on op type. **Zero
extra FIB state for Allreduce vs Reduce + Multicast separately.**

### 10.4 Allgather collective

Every member sources its slice of data; every member receives
all |G| slices.

**Implementation: |G| pipelined broadcasts** on the same per-
group tree.

- For each member m: m broadcasts its slice using the v2 phase-
  two multicast machinery.
- Total of |G| broadcasts; each member receives |G|−1 packets
  (one from each other member).

**FIB**: completely unchanged from phase two. RPF naturally
handles different sources because the (m') tree is root-agnostic.

**New in phase three**:
- `start_allgather` parser token.
- Driver branch that schedules |G| `UecBcastSrcMcast` instances,
  one per member, with shared barriers.
- Possibly a `BarrierTrigger`-of-BarrierTriggers structure to
  signal "all |G| broadcasts complete."

**Cost**: nearly free. The switch-side code is unchanged from
phase two. The orchestration layer adds ~50 lines of driver code
plus parser support.

This is the cheapest grade-5.25 milestone available — Allgather
"comes for free" given (m')/RPF multicast.

### 10.5 Packet format extensions for phase three

Required new packet fields (or new packet types):

- **Operation type**: distinguishes multicast / reduce / allreduce-
  up / allreduce-down / allgather. Could be a packet-type enum
  value, a header field, or a dst-range partition.
- **Operation sequence number**: distinguishes concurrent
  aggregations on the same group. Per-source counter.
- **Partial reduction state**: the small operand carried with
  reduction packets. Size depends on reduction operator and
  data type — for single-MTU thesis scope, a few bytes.
- **Reduction root identifier** (for reduce/allreduce): which
  host is the root of this op.

These are the proposal's deliverable §3.2 ("integrating
multicast/aggregation metadata support into the htsim packet
format"). v3 phase two doesn't need any of them; phase three
designs and implements the format.

### 10.6 Validation against phase-two architecture

The v3 FIB shape (`INCFibEntry` with `tree_port_mask` +
`root_port_idx` + `host_rewrites`) supports:

- ✅ Multicast / Broadcast (phase two): `tree_port_mask`,
  `host_rewrites`.
- ✅ Reduce: `tree_port_mask`, `root_port_idx` per (group, reduce-
  root).
- ✅ Allreduce: phase A uses tree_port_mask + root_port_idx; phase
  B uses tree_port_mask + ingress. Same FIB.
- ✅ Allgather: phase-two multicast invoked |G| times. Same FIB.

Storage scaling:

- Multicast-only group: 16 bytes mask + small rewrites.
- Group used for reduce/allreduce: 16 bytes mask + small
  rewrites + ~|reduction_roots| × 1 byte for root_port_idx
  table (typically just 1 root per group).

**Conclusion**: the v3 design is forward-compatible with all four
phase-three operations the thesis targets. Adopting it now —
rather than perfecting a multicast-only shape and rewriting later
— is the time-efficient path to grade 5.25 within the proposal's
budget.
