# Phase-Two Plan v2 — Switch-Level Multicast with Reverse Path Forwarding

*Proposal v2. Supersedes `v1.md` on §3.6 and the
sections that depend on it. The replication model — (β) tree
replication, §3.1 — is unchanged. The change is in **how multicast
state is keyed and dispatched**: instead of one directed tree per
`(root, group_idx)` pair, v2 installs one undirected tree per
`group_idx` and uses **Reverse Path Forwarding (RPF)** at fanout
time to compute egress directions from the packet's ingress port.
This matches how real switch ASICs do multicast and unlocks
per-group (rather than per-(root, group)) state scaling.*

*The cascading consequences are documented in §3.3, §3.4, §3.5,
§4, §5, §7. No code has been written. Please approve, amend, or
reject.*

---

## 0. What Changed Relative to v1

| Aspect | v1 | v2 |
|---|---|---|
| Tree granularity (§3.6) | One directed tree per `(root, group_idx)` | One undirected tree per `group_idx` |
| Dispatch model | Pre-committed egress routes per branch | RPF: replicate to all tree ports except ingress |
| Mcast destination encoding | `mcast_dst(root, group_idx)` | `mcast_dst(group_idx)` |
| FIB state per switch | O(\|groups\| × \|distinct_roots_per_group\|) | O(\|groups\|) |
| Tree-construction constraint | Any path-set valid per root | **Must be root-agnostic** (deterministic AGG/Core selection) |
| Leaf-TOR `_flow_id` rewrite (§3.5) | Required (per-leg flow_id) | **Eliminated** (op-level flow_id passes through) |
| Sink registration | Per-(op, member) under derived `leg_flow_id` | Per-(op, member) under op-level `flow_id` |
| Architectural fidelity to ASIC multicast | Faithful in timing, idiosyncratic in state shape | Faithful in timing **and state shape** |

The phase-one harness, sink/barrier orchestration, and the
`UecBcastSrcMcast` source-class boundary (§3.7) are unchanged from
v1. Step-1 / step-6 / step-9 of the implementation plan are
unchanged. Steps 2, 3, 4, 5, 7 change substantively.

## 1. Recap: What Phase One Delivers, What Phase Two Must Add

Phase one (merged) emulates `MPI_Bcast` by decomposing one broadcast
into \|G\|-1 unicast legs. The root runs \|G\|-1 `UecBcastSrc`
instances and pushes \|G\|-1 packets out of its 100 Gbps uplink, one
after another. That serialisation is the bottleneck and produces
the linear completion-time curve reported in Chapter~4.3 of the
thesis (≈339 ns per added leg).

**Phase two introduces the network-side multicast mechanism.** The
root emits *one* packet; the fabric replicates it so that \|G\|-1
copies are delivered without the root-uplink bottleneck. The
completion-time curve should become approximately *constant* in
\|G\|, dominated by the farthest leaf's path latency and the
worst-case branching factor, not by linear-in-\|G\| serialisation.

The phase-one benchmark harness and the sink/barrier completion
orchestration are carried over **unchanged**. Only the sending
endpoint and the fabric-internal routing change.

## 2. Ground Truth from the Codebase (agent findings)

### 2.1 Switch forwarding is two-stage and strictly unicast

`FatTreeSwitch::receivePacket` (`fat_tree_switch.cpp:23`) runs a
two-step pipeline per packet:

1. **Ingress**: look up FIB via `getNextHop(pkt)`
   (`fat_tree_switch.cpp:321`), attach the chosen `Route` to the
   packet, then delay via `_pipe->receivePacket(pkt)`.
2. **Egress**: remove from `_packets` tracking and `pkt.sendOn()`
   along the attached route.

The FIB is strictly destination-keyed:
`RouteTable::_fib : unordered_map<int, vector<FibEntry*>*>`
(`routetable.h:52`). The `vector<FibEntry*>` is the ECMP
alternatives list; `getNextHop` picks exactly one of them via a
hash of `flow_id` and `pathid`. Packets carry single-path state
(`_dst`, `_pathid`, `_route`, `_nexthop`) and take exactly one
route per hop. **No code path anywhere in htsim fans a single
packet out to multiple egress ports today.**

Critically for v2: `FatTreeSwitch::getNextHop(Packet&, BaseQueue*
ingress_port)` already accepts an ingress-port argument, but
`receivePacket` calls it with `NULL` (line 44). The plumbing for
ingress-aware routing is *partially* in place; v2's RPF dispatch
needs to thread the actual ingress queue through.

### 2.2 `FatTreeTopology::set_up_mcast` is a no-op stub, correctly placed

Defined at `fat_tree_topology.cpp:596`, printing
`"set_up_mcast unimplemented"` when `groups != nullptr`. It is
invoked from `main_uec.cpp:781`, after the topology is built and
`conns->groups` is attached, but *before* any per-flow `UecSrc` /
`UecSink` is instantiated. Under v2 this ordering is **load-bearing
and correct** because per-group tree construction depends only on
group membership and topology — it does *not* need access to sink
objects.

The topology exposes:

- `switches_lp / switches_up / switches_c` for TOR / AGG / CORE
  switches respectively;
- `queues_ns_nlp`, `queues_nlp_nup`, `queues_nup_nc`, and their
  reverses — `[from_tier_id][to_tier_id][bundle]` indexed;
- `HOST_POD_SWITCH(host)`, `MIN_POD_AGG_SWITCH(pod)`,
  `MAX_POD_AGG_SWITCH(pod)`;
- `FatTreeSwitch::switch_type` (`TOR` / `AGG` / `CORE`) via
  `getType()`.

Everything needed to compute an undirected replication tree
deterministically is available.

### 2.3 Packets have a ref-count that could support non-clone fanout…

`PacketDB` uses `inc_ref_count` / `dec_ref_count`
(`network.h:274–312`): a packet is only freed when the refcount
reaches zero. In principle one packet object could be delivered to
multiple egress ports with `inc_ref_count(N)` and each
queue/sink decrementing on consumption. **This is what real ASICs
do** with one buffer in shared memory and N descriptors pointing
at it.

### 2.4 …but fanout *must* use distinct packet objects, not one shared

A single htsim `Packet` carries path state (`_route`, `_pathid`,
`_nexthop`, `_direction`) **fused with the body**. Different
replicas take different paths and must have different values for
those fields. Sharing one packet object across replicas therefore
does not work. The simulator's `Packet` abstraction conflates what
real hardware separates into "buffer cell" + "egress descriptor";
without splitting that abstraction (a cross-transport refactor),
distinct copies are the only option.

`UecPacket::newpkt(UecPacket &source)` (`uecpacket.h:45`) exists as
a copy factory, but as written it sets `size = acksize` (header
only) and copies the source's route — both wrong for full-payload
fanout replicas. v2 introduces a sibling factory `newpkt_replica`
(see §5 step 3).

### 2.5 No pre-existing multicast anywhere

Searched `uec.cpp`, `eqds.cpp`, `ndp.cpp`, `tcp.cpp`, `roce.cpp`,
`swift.cpp`, `hpcc.cpp`, `strack.cpp`, `switch.cpp`,
`compositequeue.cpp`, `queue.cpp`, `tests/`. No replication,
fanout, or multicast route support outside the stub. Tests do not
exercise one-to-many delivery. Phase two is a from-scratch
extension.

### 2.6 Consequence for the design

The cleanest structural insertion point is
`FatTreeSwitch::getNextHop` + `FatTreeSwitch::receivePacket`:
teach them that a specific class of destinations means "fan me
out to all tree-member ports except the one the packet arrived
on". The replication unit is one fresh `UecPacket` per egress,
produced via a new `UecPacket::newpkt_replica` copy factory.

Under v2 the **ingress port** becomes a first-class input to the
fanout decision. The switch must identify which physical port the
packet entered through; the FIB entry then provides the **set** of
tree-member ports; RPF computes the egress set as `tree_ports \
{ingress}`. No directed routing decisions are baked into the FIB.

## 3. Design Decisions

Each decision lists the alternatives, the trade-offs, and a
recommendation. All recommendations are subject to approval.

### 3.1 Where does replication happen?

**Three candidates.** *(Unchanged from v1.)*

- **(α) Ingress-only at the root's TOR.** The root's TOR sees one
  incoming packet and emits \|G\|-1 copies toward the destination
  TORs directly.
- **(β) Tree replication.** Every switch on the multicast tree
  receives one packet and emits one copy per non-ingress tree
  port (typically 2–K copies). Matches real hardware (NVIDIA SHARP,
  Broadcom Scorpion).
- **(γ) Hybrid.** Ingress fans out by pod; per-pod AGGs fan out by
  TOR.

(α) is the simplest but **reintroduces the same root-uplink
bottleneck phase one has**: the root's TOR still serialises \|G\|-1
packets out of its uplinks. Rejected.

(γ) is a two-level special case of (β). Simpler but adds no
structural benefit.

**Recommended: (β) tree replication.** Each switch along the tree
emits one packet per non-ingress tree port. This is what gives the
constant-time completion-time curve the thesis wants to compare
against the baseline. It is also how real hardware multicast
works.

### 3.2 How does a packet signal "I need multicast fanout"?

**Three candidates.** *(Unchanged from v1, except the encoding
content.)*

- **(i) New `Packet::ptype` value**, e.g. `UEC_MCAST`.
- **(ii) Reserved destination-address range.** Group identifiers
  live in a disjoint subrange of `_dst`.
- **(iii) Flag on the packet.**

(i) and (iii) require every switch site to check an extra field
and branch. (ii) drops into the existing
`_fib->getRoutes(pkt.dst())` path without any ingress-side
changes; only the lookup *result* needs a new interpretation.

**Recommended: (ii) reserved destination range.** Define
`MCAST_BASE = 0x80000000` (assert `> topology->no_of_nodes()` at
`set_up_mcast` start). Synthesise group identifiers
`mcast_dst(group_idx) = MCAST_BASE | group_idx`.

**Change from v1**: the destination encodes `group_idx` only. The
root identity is *not* in the destination, because under (m') the
same FIB entry serves all roots that source into this group. This
is the user-visible cascade of the §3.6 change: dst is per-group,
not per-(root, group).

### 3.3 FIB representation for multicast

**Three candidates.** *(Recommendation unchanged: still (q). The
internal data shape changes.)*

- **(p) Extend `FibEntry` with a fanout list** — one entry carries
  all egress ports.
- **(q) New `McastFibEntry : FibEntry`** subclass.
- **(r) Reuse `vector<FibEntry*>`, mark it multicast.**

(r) is type-unsafe: existing ECMP-traversing code (`adaptive_route`,
`permute_paths`, comparator functions) would silently misroute on
mcast vectors. Rejected.

(q) is the cleanest. Subclass makes the semantic explicit;
`McastFibEntry::getEgressPort()` can `assert(0)` so legacy code
that accidentally treats the entry as ECMP crashes loudly instead
of silently misrouting.

**Recommended: (q) `McastFibEntry : FibEntry`**, with `getRoutes()`
returning `vector<FibEntry*>` unchanged. On a multicast destination
the vector contains one `McastFibEntry` rather than several
`FibEntry`s.

**Change from v1 — internal data shape:**

```c
class McastFibEntry : public FibEntry {
public:
    struct TreePort {
        Route* egress;             // route ending at the next-hop
                                   // BaseQueue (or at the host queue
                                   // for leaf-TOR member ports)
        BaseQueue* port_queue;     // used for ingress comparison
                                   // (RPF check)
        std::optional<int> rewrite_dst;  // host_addr if this is a
                                          // leaf-TOR member port;
                                          // nullopt for interior tree
                                          // ports
    };
    const std::vector<TreePort>& getTreePorts() const { return _ports; }

    Route* getEgressPort() override {
        assert(0 && "McastFibEntry has multiple egress routes; "
                    "use getTreePorts()");
        return nullptr;
    }
private:
    std::vector<TreePort> _ports;  // undirected port set; egress
                                   // direction is computed at fanout
                                   // time as ports \ {ingress}
};
```

The vector is **unordered, undirected, and ingress-agnostic**. The
same entry serves any source that legitimately enters this switch
on any tree port.

### 3.4 Packet replication mechanism

**Two candidates.** *(Recommendation unchanged: still (v). RPF
dispatch detail added.)*

- **(u) Ref-count sharing.** Call `inc_ref_count(N-1)` on the
  arriving packet; queue the same pointer on N egress ports.
- **(v) Distinct copies.** Spawn N-1 fresh packets from the
  PacketDB pool; each copy carries its own per-replica path state.

(u) is rejected by the simulator's abstraction: `Packet` fuses
body and per-recipient state. Real ASICs implement (u) by storing
per-recipient state on a separate descriptor; htsim doesn't have
that split.

**Recommended: (v) distinct copies.** Dispatch:

1. **Identify the ingress port** (see §4 plumbing). Identify which
   `BaseQueue*` the packet arrived on at this switch.
2. **Look up the `McastFibEntry`** via `_fib->getRoutes(pkt.dst())`.
3. **Compute `egress_set = tree_ports \ {ingress}`** by iterating
   `getTreePorts()` and skipping the entry whose `port_queue ==
   ingress`.
4. **For each `port` in `egress_set`**:
   - Spawn a replica via `UecPacket::newpkt_replica(src,
     port.egress, port.rewrite_dst.value_or(pkt.dst()),
     branch_pathid)`.
   - Reset `_direction = NONE` on the replica (let the next hop
     re-establish via `set_direction`).
   - At leaf-TOR member ports (where `rewrite_dst` is set), the
     `egress` route in `TreePort` already terminates at the host
     queue chain; the replica's `_dst = host_addr` then matches
     the existing host-fib state at the destination's TOR (see
     §3.5 (x)).
   - Mark `_packets[replica] = true` **before** dispatch through
     `_pipe`; otherwise the pipe-callback path will re-classify
     the replica as a new ingress arrival and loop.
   - Send via `_pipe->receivePacket(*replica)`.
5. **The original packet** is reused for one branch (the first
   non-ingress entry by convention) to save one allocation, OR is
   freed and replaced by a fresh replica for symmetry. Symmetric
   handling is recommended in v2 to avoid the asymmetric
   `_direction`-reset hazard the v1 plan glossed over.

**Note on `_pathid` per replica**: v1 justified per-replica
`_pathid` rewriting as "independent ECMP entropy upstream." Under
(β) tree replication with fully-installed `McastFibEntry` state
*and* RPF dispatch, **the multicast path consults neither
`_pathid` nor `flow_id` for routing**. Setting per-replica
`_pathid` is purely cosmetic — useful for distinguishing replicas
in trace logs, no effect on routing. This is acknowledged
explicitly in v2 rather than presented as a routing benefit.

### 3.5 Leaf-TOR delivery to hosts

At the leaf TOR for a member host `h`, the multicast packet must
be delivered to the sink registered for `(h, op_flow_id)`. Three
candidates:

- **(x) Rewrite `_dst` to each host address at the leaf TOR.**
  Replicas emerge with `_dst = h` and the existing host-fib
  machinery routes the last hop unchanged.
- **(y) Install per-host `McastFibEntry` egress routes whose last
  hop is the host queue itself.** Per-(host, op) sink baked into
  the FIB.
- **(z) Introduce a new "mcast-aware" sink** that accepts packets
  with `_dst = mcast_id` and matches by `flow_id`.

(z) requires wiring the sink dispatch into the multicast-dst path
without simplifying anything else. Rejected.

(y) defeats the per-group state simplification: it re-introduces
per-(group, op) FIB entries because each op has its own sink
identity. Rejected.

**Recommended: (x) rewrite `_dst` per host at the leaf TOR.**

**Change from v1 — `_flow_id` is NOT rewritten.** v1's design had
the leaf-TOR rewrite produce both `_dst = host_addr` *and*
`_flow_id = leg_flow_id` so that sinks could be registered under
synthesized per-leg flow_ids. v2 simplifies this:

- The op-level `flow_id` (set by the source's `_flow`) passes
  through unchanged. Replicas inherit the source's `_flow` via
  `newpkt_replica`.
- Sinks at member TORs are registered via
  `addHostPort(host_addr, op_flow_id, sink)` — the op's own
  flow_id, not a derived leg id.
- At the leaf TOR, after the replica has `_dst = host_addr`,
  `getNextHop` is **re-invoked** (or the host-fib lookup is done
  inline). The lookup `getHostRoute(host_addr, pkt.flow_id())`
  with `pkt.flow_id() == op_flow_id` returns the route ending at
  the correct sink.

This works because `(host_addr, flow_id)` is the existing
host-fib key, and `(host_addr, op_flow_id)` is unique across all
concurrent operations in the simulation. No per-leg flow_id
namespace is needed.

The leaf TOR's `McastFibEntry` only needs to mark each member
host port with `rewrite_dst = host_addr`; it does **not** carry
sink pointers or per-op state.

### 3.6 Tree granularity — **the v2 change**

**Three candidates.**

- **(m) One static tree per group, directed.** A single FIB entry
  per group, with pre-committed egress routes. Rejected by v1 for
  the right reason: directed egress routes depend on the source's
  position, and a static entry can't encode multiple source
  cases.
- **(n) One tree per `(root, group_idx)` pair.** v1's
  recommendation. Tighter state granularity but also tighter
  storage.
- **(m') One undirected tree per `group_idx`, RPF dispatch.**
  Single FIB entry per group, storing the **set** of tree-member
  ports at each switch. Egress directions computed at packet-
  receive time as `tree_ports \ {ingress_port}`. Matches real
  hardware multicast (PIM-SSM, Ethernet bridge multicast,
  NVIDIA SHARP).

**Recommended: (m') one undirected tree per group, with RPF.**

#### Rationale

1. **Architectural fidelity.** Real switch ASICs store undirected
   port sets (or port bitmaps) for multicast groups; the egress
   direction is implicit in which port the packet arrived on. v1's
   (n) design — pre-committed directed egress lists per (root,
   group) — is unique to the simulator and would be a fidelity
   gap if the thesis claims "phase two faithfully models switch-
   level multicast as it works in production hardware."

2. **State scaling.** v1 (n) installs O(\|groups\| ×
   \|distinct_roots_per_group\|) entries across the fabric. v2
   (m') installs O(\|groups\|) entries. For a workload that
   exercises only one root per group (typical of the thesis sweep
   as currently designed), the cardinality is the same, so this
   isn't a near-term win — but if phase three or later extends to
   collectives where multiple members can source (allgather,
   reduce-scatter, allreduce), v1's (n) state explodes while v2
   (m') stays compact.

3. **Composability with future collectives.** A group-FIB keyed
   by `group_idx` alone is the right shape for any collective
   that operates over a fixed group. Allreduce trees, scatter
   trees, gather trees can all be installed under the same
   per-group-id key, with operation-specific dispatch logic
   (reduction, etc.) layered on top.

4. **Simpler driver code.** v1 required deriving per-leg
   `flow_id`s and registering sinks under those derived ids. v2
   uses op-level `flow_id` directly (see §3.5), eliminating one
   layer of bookkeeping in `main_uec.cpp`.

#### Cost / constraint

The tree-construction algorithm must produce an **undirected,
acyclic, root-agnostic** tree per group. Concretely: for the same
group, the same set of switches and the same set of links must
appear regardless of which member sources. This is a real
constraint on the algorithm but is trivial to satisfy in fat-tree
(see §5 step 4): pick deterministic AGG and Core convergence
points based on `group_idx`.

If the algorithm produces a non-root-agnostic tree (e.g., picks
paths starting from the root using ECMP-style hashing on
root-specific values), then different sources see different trees
and the simple "skip ingress" RPF rule fails. v2's algorithm
forecloses this by construction.

#### What v2 does **not** import from real-world multicast

We use the simplest form of RPF: "drop replicas to the ingress
port; otherwise replicate to all tree-member ports." We do **not**
implement:

- **Source-specific RPF check** (drop packets that arrive on a
  port that isn't the expected reverse-path-toward-source). Under
  assumption (A1) (single broadcast in isolation, no failures),
  there's no risk of misrouted packets entering on a non-tree
  port.
- **Loop suppression beyond skip-ingress.** Our trees are
  shortest-path subgraphs of a fat-tree, which are inherently
  acyclic. No cycle can form unless tree construction is buggy.
- **Multi-source shared-tree semantics with RP** (PIM-SM style).
  Each group has one tree; any member can source into it without
  reconfiguration, but the RPF check is just "don't echo the
  ingress."

These restrictions are appropriate to the thesis scope (assumption
A1, A3 — see §1, §8). They are flagged explicitly in §8 as
non-goals.

*(Unchanged from v1.)*

**Recommended: (τ) new `UecBcastSrcMcast`.** A new CLI flag

class is instantiated in the `is_bcast` branch of `main_uec.cpp`.
The completion barrier, the sinks, the recorder, and the

## 4. Chosen Architecture (subject to approval)

Stitching the v2 recommendations together:

1. **Source.** `UecBcastSrcMcast : public UecSrc` (new class in
   `uec_bcast.{h,cpp}`) emits exactly one packet per `.cm`
   broadcast entry. The source's `_flow` carries the op-level
   `flow_id`. `_dst` is set to `mcast_dst(group_idx)`.

2. **FIB.** `McastFibEntry : public FibEntry` (new class in
   `routetable.{h,cpp}`) holds an unordered `vector<TreePort>` —
   each tree-member port at this switch, with optional
   `rewrite_dst = host_addr` flags for leaf-TOR member ports.
   `getEgressPort()` is overridden to assert (defensive against
   legacy ECMP code paths).

3. **Switch dispatch (RPF).**
   - `FatTreeSwitch::receivePacket` is extended to track the
     ingress queue. Two implementation options:
     - **(A)** Inspect `pkt.route()->at(pkt.nexthop() - 2)` to
       identify the upstream queue, then map it via a per-switch
       `unordered_map<BaseQueue*, port_index>`.
     - **(B)** Change the `BaseQueue → switch` handoff to call a
       new overload `receivePacket(Packet&, BaseQueue*
       ingress_queue)`. Cleaner but touches the queue→switch
       interface.
   - Recommended: (A) for phase 2; (B) is a possible follow-up
     refactor if ingress info is needed elsewhere.
   - On detecting an `McastFibEntry` from `getNextHop`, the
     switch enters the fanout path (§3.4). For each non-ingress
     tree port, it spawns a replica with the port's egress route
     and (for leaf-TOR member ports) `_dst = host_addr`. Each
     replica is marked in `_packets`, sent through `_pipe`, and
     handled by the existing egress branch on pipe callback.

4. **Topology setup.** `FatTreeTopology::set_up_mcast` walks
   `conns->groups` (NOT `conns->connections`). For each group:
   - Build a deterministic, root-agnostic, undirected tree
     (algorithm in §5 step 4).
   - Install one `McastFibEntry` on each switch on the tree,
     keyed by `mcast_dst(group_idx)`. Entries store the per-switch
     tree-member port set.

5. **Sinks and barrier.** Unchanged from phase one. Still
   `UecBcastSink` per group member, still one `BarrierTrigger`
   with `count = |G|-1`, still the `BcastCompletionRecorder`.
   **Sinks are registered under the op-level `flow_id`**, not a
   derived `leg_flow_id`. This is a simplification relative to v1.

6. **Driver.** New `-bcast_mode {baseline,mcast}` CLI flag on
   `htsim_uec`. In the `is_bcast` branch of `main_uec.cpp`:
   - `baseline` (default): current \|G\|-1-leg path, unchanged.
   - `mcast`:
     - Allocate one `UecBcastSrcMcast` with op-level `flow_id`.
     - Register the source at the root's TOR via
       `addHostPort(root, op_flow_id, src)`.
     - For each group member `m ≠ root`: allocate a
       `UecBcastSink`, register at member's TOR via
       `addHostPort(m, op_flow_id, sink)`. (Same flow_id as
       source — the (host, flow_id) tuple is unique across
       members because hosts differ.)
     - Wire all sinks to one `BarrierTrigger` exactly as in
       phase one.

#### v1→v2 driver-side simplification

v1 required deriving per-leg `flow_id`s for sinks
(`++next_bcast_leg_flow_id`) and rewriting `_flow_id` at the leaf
TOR. v2 eliminates both: sinks register under the op's own
`flow_id`, and no rewrite is needed because the op flow_id is
already in the packet via the source's `_flow`. Remove the
`next_bcast_leg_flow_id` machinery in mcast mode (keep it for
baseline mode).

#### Ordering note on `set_up_mcast`

Under v2, `set_up_mcast` requires only group membership and
topology — no sink objects. The current call site
(`main_uec.cpp:781`, before the bcast loop) is correct and
unchanged. v1 had a latent ordering hazard around leaf-TOR sink
routes that v2 eliminates.

## 5. Implementation Plan

Ordered so each step is independently testable. Steps 1, 6, 8, 9,
10 are largely unchanged from v1. Steps 2, 3, 4, 5, 7 change
substantively.

1. **Multicast address space** *(small, isolated)*.
   - Add `mcast_dst(group_idx) -> uint32_t` helper in
     `uec_bcast.h`. **Single argument** — root is not encoded.
   - Add `Packet::is_mcast()` (range check on `_dst` against
     `MCAST_BASE`).
   - Unit test: round-trip encode/decode; assertion that
     `MCAST_BASE > topology->no_of_nodes()`.

2. **`McastFibEntry`** *(small, no behavioural change)*.
   - New class in `routetable.{h,cpp}`; holds `vector<TreePort>`
     where `TreePort = {Route*, BaseQueue* port_queue,
     optional<int> rewrite_dst}`.
   - Override `getEgressPort()` to assert.
   - Provide `getTreePorts()` accessor.
   - Does not yet appear in any FIB.

3. **Ingress-aware fanout in `FatTreeSwitch`** *(focused diff,
   moderate complexity — this is the main behavioural change)*.
   - Add `unordered_map<BaseQueue*, port_index>` to
     `FatTreeSwitch`, populated at construction from `_ports`.
   - In `receivePacket`, identify ingress: walk back through
     `pkt.route()` to find the upstream queue (the element at
     index `nexthop - 2` is the queue that just delivered the
     packet to this switch).
   - In `getNextHop`: if the FIB result for `pkt.dst()` contains
     an `McastFibEntry`, return it as-is (skip ECMP selection).
   - Add a new `UecPacket::newpkt_replica(source, branch_route,
     branch_dst, branch_pathid)` factory in `uecpacket.h` that
     produces a full-data replica with overridable route, dst,
     and pathid. Don't touch the existing `newpkt(source)` —
     that's used by trim paths.
   - Implement RPF dispatch in `receivePacket`'s ingress branch
     on detection of `McastFibEntry`:
     ```c
     for (auto& port : entry->getTreePorts()) {
         if (port.port_queue == ingress) continue;
         UecPacket* replica = UecPacket::newpkt_replica(
             *static_cast<UecPacket*>(&pkt),
             *port.egress,
             port.rewrite_dst.value_or(pkt.dst()),
             pkt.pathid() + i);   // cosmetic, for tracing
         replica->set_direction(NONE);
         _packets[replica] = true;
         _pipe->receivePacket(*replica);
     }
     // Free or reuse the original; recommended: free for symmetry.
     pkt.free();
     ```
   - At leaf-TOR member ports: when `rewrite_dst` is set, the
     replica's egress route should terminate at the host queue
     chain. Two implementation options:
     - **Pre-bake the host route** in the `TreePort.egress`. At
       set_up_mcast time, build a route ending at
       `queues_nlp_ns[tor][host][bundle]` →
       `pipes_nlp_ns[tor][host][bundle]` → (terminator). The
       terminator is resolved lazily at fanout time via host-fib
       lookup `(host_addr, pkt.flow_id())` using the packet's
       op flow_id.
     - **Re-inject at the switch**: spawn the replica with
       `_dst = host_addr` and **re-run** `getNextHop`. The
       host-fib lookup picks up the right sink.
   - Recommended: re-injection. The host-fib already exists at
     the leaf TOR (populated by sink `addHostPort` calls); the
     leaf-TOR fanout doesn't need to duplicate that state in the
     `McastFibEntry`.
   - Unit test: a hand-constructed topology + hand-installed
     `McastFibEntry` fans out correctly. Inject a packet on a
     specific ingress port; assert N-1 replicas emerge on the
     N-1 non-ingress tree ports.

4. **Tree construction** *(logic, no switch changes — main new
   algorithmic content)*.
   - New helper `FatTreeTopology::build_mcast_tree(int
     group_idx)` returning, for each switch on the tree, a list
     of `TreePort`s.
   - **Reference algorithm (root-agnostic)**:
     ```
     members = conns->groups[group_idx]
     member_tors = { HOST_POD_SWITCH(h) for h in members }
     member_pods = { HOST_POD(h) for h in members }

     # Pick deterministic convergence points
     chosen_agg_in_pod[p] = MIN_POD_AGG_SWITCH(p) +
                            (group_idx % agg_switches_per_pod())
     chosen_core = group_idx % NCORE  # only if multi-pod

     # Build per-switch tree port sets:
     for tor in member_tors:
         pod = HOST_POD of any member on this tor
         agg = chosen_agg_in_pod[pod]
         add to tor's tree set:
             - host_downlink for each local member (with
               rewrite_dst = host_addr)
             - uplink to chosen_agg (no rewrite)
         add to agg's tree set:
             - downlink to this tor (no rewrite)
             - if multi-pod: uplink to chosen_core (no rewrite)

     if len(member_pods) > 1:
         add to chosen_core's tree set:
             - downlink to chosen_agg_in_pod[p] for each
               p in member_pods (no rewrite)

     # Verify acyclicity and root-agnosticism by construction:
     # - Each TOR appears once with degree = (#local members) +
     #   (1 if pod has uplink else 0).
     # - Each AGG appears once per relevant pod with degree =
     #   (#member-TORs in pod) + (1 if multi-pod else 0).
     # - Core appears once if multi-pod with degree =
     #   (#member-pods).
     # - The undirected graph is a tree (no cycles).
     ```
   - Edge cases:
     - All members on one TOR: tree is just the TOR with host
       downlinks; no AGG/Core.
     - Single-pod multi-TOR: tree includes one AGG, no Core.
     - Multi-pod: full three-level tree.
     - 2-tier topology (no Core): special-case (Core branch
       skipped, tree spans TOR and AGG only).
   - Unit test: K=4 fat-tree, group spanning two pods, check the
     tree has the expected switches and that the per-switch port
     sets contain the right tree members. Repeat for intra-pod
     and intra-TOR cases.

5. **`FatTreeTopology::set_up_mcast` body**.
   - Walk `conns->groups` (a `vector<vector<int32_t>>`); for each
     group_idx with `groups[group_idx].size() >= 2`:
     - Call `build_mcast_tree(group_idx)`.
     - For each `(switch_ptr, tree_ports)` in the result, install
       an `McastFibEntry` keyed by `mcast_dst(group_idx)` on that
       switch's FIB.
   - Fail with a clear message if a group member is unreachable
     (shouldn't happen in a complete fat-tree, but safety).
   - **Note**: `set_up_mcast` does **not** look at
     `conns->connections` (the per-op list); it only reads
     `conns->groups`. The same per-group state serves all ops on
     that group regardless of which member sources. v1 walked
     `connections` to collect `(root, group_idx)` pairs; v2
     ignores root identity at this layer.

   - Does NOT touch existing `UecBcastSrc`.

## 6. Benchmark and Expected Outcome

*(Unchanged from v1.)*

Sweep parameters match phase one (3 fat-trees × up to 10 group
sizes × 10 reps × 4 KB payload × 100 Gbps). With
`-bcast_mode mcast`, the expected completion-time curve is:

- **Constant in \|G\|** to within the spread of group-membership
  path lengths. The root emits one packet; fabric replication
  turns that into \|G\|-1 deliveries whose completion is the
  *max* of per-leaf path latencies, not a sum.
- **Sensitive to group *layout*.** Unlike phase one, where
  root-serialisation masked path effects, phase two's completion
  is exactly the slowest leaf's path latency. Intra-pod groups
  finish faster than cross-pod groups. Variance across reps
  should now be visible.
- **Topology size matters (slightly).** Larger fat-trees have
  more hops per cross-pod path, so the curves will separate
  slightly, unlike in phase one where they overlapped.

If the measured curve is *not* roughly constant in \|G\|, that is
a bug: something along the mcast path is still serialising.

## 7. Risks and Open Questions

- **Concurrent broadcasts sharing links.** Phase-two replication
  places multiple replicas on shared interior links. Under
  heavy offered load the root's uplink is no longer the
  bottleneck, but interior AGG/CORE uplinks might become one.
  Phase-two measurements with a single broadcast in isolation
  are cleanest first. Under (m'), concurrent broadcasts on the
  same group share the per-group tree (same interior switches,
  same links), which makes interior contention more concentrated
  than under (n) where different (root, group) pairs could spread
  across different trees. Worth surfacing in the thesis if it
  matters.

- **Packet identity in tracing.** `_packets` at each switch keys
  on a packet pointer; the fanout path introduces N-1 distinct
  pointers at a switch. Each replica must be inserted into
  `_packets` before being passed to `_pipe`, otherwise the
  pipe-callback path mis-classifies the replica as a new ingress
  arrival. Unit test covers this.

- **Ingress port identification correctness.** The RPF dispatch
  depends on correctly identifying which port the packet arrived
  on. The route-inspection approach (`pkt.route()->at(nexthop -
  2)`) needs the upstream queue to be a port queue of *this*
  switch; verify with a unit test that traverses
  `_ports` to confirm the back-pointer matches a known port.
  Under failures or unusual route shapes this could yield
  surprises; flag as a property to assert.

- **Tree must be undirected acyclic and root-agnostic.** The v2
  algorithm in §5 step 4 satisfies this by construction. If the
  algorithm is ever changed (e.g., to load-balance better
  across trees), the new algorithm must preserve these
  properties. Add an invariant check in `build_mcast_tree`: the
  resulting per-switch port sets, viewed as an undirected graph,
  must form a tree.

- **`_direction` state machine on replicas.** Each replica's
  `_direction` is reset to `NONE` at fanout. The next switch
  along the replica's egress route then sets `UP` or `DOWN`
  based on the egress port. Verify that the existing
  `Packet::set_direction` assert (rejects `DOWN→UP`) is never
  tripped on the multicast path. By the geometry of fat-tree
  shortest-path trees, this should hold: a packet goes up to
  its peak interior switch, then only down. Confirm with a
  unit test that traces direction transitions.

- **`main_uec.cpp` already allocates a root-side `UecSrc`
  anyway.** In mcast mode the root-side object is just one
  instead of \|G\|-1, which is cheaper. Not a risk, just noting.

- **`MCAST_BASE` safety vs. topology node count.** Choose
  `MCAST_BASE` so that it is unambiguously above any possible
  host id (`topology->no_of_nodes()` returns the bound). Assert
  at `set_up_mcast` start.

- **(Removed from v1)**: the v1 risk about "ECMP picks the same
  CORE for two branches" is **eliminated** under v2. The tree
  is pre-installed and ECMP is bypassed entirely on the mcast
  path. The §3.4 mention of per-replica `_pathid` is now
  acknowledged as cosmetic-only.

- **(Removed from v1)**: the v1 risk about `set_up_mcast` /
  sink-registration ordering is eliminated because v2's
  `set_up_mcast` doesn't depend on sink objects.

## 8. Non-Goals for Phase Two

- Other collectives (Scatter, Gather, Reduce, Allreduce). Their
  switch-level primitives can share the group-FIB mechanism
  introduced here, but their send/completion logic differs. Out
  of scope.
- Congestion control and trimming on multicast packets.
  Assumption (A3) (infinite switch buffers) remains in effect.
  Real-hardware multicast interacts with backpressure in a
  specific way; that is its own sub-project. The v2 design does
  not foreclose adding finite-buffer modeling later — see the
  earlier discussion on tier-1/tier-2 buffer fidelity.
- Multi-root or any-to-all schedules within a single operation.
  Phase two stays single-root per operation. Note that under
  (m'), multiple operations on the same group with different
  roots are supported naturally — each operation has its own
  source, sinks, and barrier; the per-group FIB serves all of
  them.
- Failure injection on multicast paths. The `failure` machinery
  in `ConnectionMatrix` is orthogonal. Note: under failures, a
  full PIM-style RPF check (drop packets arriving on
  not-toward-source ports) would be needed to suppress loops.
  Phase two assumes (A1) no failures; the simple "skip ingress"
  RPF rule suffices.
- Source-specific RPF check. We use the simplest skip-ingress
  rule. Real PIM-SSM does an RPF check against the specific
  source's reverse path; under (A1) and acyclic trees, this is
  unnecessary.
- Packet-format changes beyond adding a "this is multicast" bit
  (via `_dst` range).

## 9. Stopping Here for Approval

Please review v2 specifically against v1. Pointed questions:

1. Is the move to **(m')/RPF** the right call given the
   architectural-fidelity argument? Or is v1's (n) preferred for
   the thesis on grounds of implementation simplicity (no
   ingress threading, pre-committed routes)?

2. The deterministic AGG/Core selection in §5 step 4 uses
   `group_idx % agg_switches_per_pod()` and `group_idx % NCORE`.
   This load-balances trees across groups but is naive. Is this
   sufficient for the thesis sweep, or should tree placement
   consider per-group member layout (e.g., minimize cross-pod
   traversal)?

3. The leaf-TOR rewrite uses **only `_dst`**, not `_flow_id`
   (§3.5). Sinks register under op-level `flow_id`. Is this
   simplification acceptable, or are there concurrent-operation
   workloads where the (host, op_flow_id) tuple isn't unique?
   (I claim it is unique because hosts differ per member and
   op_flow_id differs per operation, but please sanity-check.)

4. Ingress port identification via route inspection (v2 §4 (A))
   vs. signature change to `receivePacket(Packet&, BaseQueue*)`
   (v2 §4 (B)). (A) is less invasive; (B) is cleaner. Preference?

5. Any decision you want to flip, or additional design
   considerations to bake in before step 1?
